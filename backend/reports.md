# Reports

The **design report** (方案汇报) is the product's flagship output: a polished
HTML document that turns AI renderings plus project assets into a client-ready
proposal. Reports are rendered **server-side** and viewed in a `web-view`
inside the mini program.

## Report architecture

```
design job (report) ─► report items config ─► Jinja2 template ─► HTML
                          ▲                        ▲
        report assets (storage) ──────────────────┤
                          │                        │
        report library / discovery ───────────────┘
```

Key modules:

| Module | Role |
| --- | --- |
| `report_config.py` | Global + workspace report configuration (item list) |
| `report_templates.py` | Report **HTML templates** (validated, sandboxed Jinja2) |
| `report_template_*.py` | Template lifecycle: bootstrap, promotion, reconciliation |
| `report_view.py` | View-token issuance/decoding + HTML rendering with CSP |
| `report_library.py` / `report_discovery.py` | Report asset library & discovery |
| `report_descriptions.py` | Human-readable item descriptions |

## Report items

A report is composed of **report items**, configured on the server. Each item
has a `key`, a display name, and a **source**:

- `source: "oss"` — an asset set under a base path (e.g. project cover, team
  showcase, renderings, mood board).
- `source: "provider"` — generated by the AI provider via a prompt template
  (e.g. **colored floor plan**, **circulation plan**).

The default global item list (from docker-compose `REPORT_ITEMS`) includes:
project cover, core strengths, team showcase, colored floor plan, circulation
plan, renderings, floor-plan layout, style/material mood board,
senior-friendly design, appliance configuration, distinctive details, smart
lighting. The list is overridable via `REPORT_ITEMS`.

## Creating a report job

A report is itself a **design job** of type `html_report`:

1. The user picks a style, fills in **client info** (surname, salutation,
   project name) and optionally selects content sections.
2. The frontend submits `POST /api/v1/design-jobs` with `type: "html_report"`
   and `report_items`.
3. The job runs through the normal pipeline (submit → provider → poll → settle);
   report-specific items that are provider-generated are rendered, and the job
   completes with a **report** attached.

## Viewing a report (short-lived bearer capability)

Reports are **not** publicly accessible. Viewing uses a **report view token**:

1. When a report job completes, the backend issues a short-lived signed
   **report view token** (`REPORT_VIEW_TOKEN_SECONDS`) bound to that
   `design_job_id`.
2. The client opens
   `GET /api/v1/design-jobs/{id}/report?token=<view-token>` in a `web-view`.
3. The backend (`report_view.py`):
   - decodes + validates the token (job match, not expired),
   - loads the job + report,
   - builds the render context (report items + asset URLs),
   - renders the **Jinja2 template** to HTML,
   - returns it with a strict **Content-Security-Policy** (nonce-based),
     `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`,
     `X-Content-Type-Options: nosniff`, and `Cache-Control: no-store`.

The mini program validates the viewer origin against
`VITE_REPORT_WEB_ORIGIN` before opening (see
[Frontend → Data Source Modes](/frontend/data-source-modes)).

## Template safety

Report templates are treated as **untrusted-ish code** and handled carefully:

- Syntax + contract validated before save.
- Rendered in a **sandboxed Jinja2 environment** (`_ReportTemplateEnvironment`).
- A **CSP nonce** is generated per render and embedded in the policy.
- Template promotion/reconciliation crons keep one validated active template
  per scope.

## Report asset library

- `report_library.py` manages the object-storage assets backing report items
  (uploads by admin/workspace owners).
- `report_discovery.py` discovers available items/assets for the client
  (`GET /report/items` style endpoint returns what a job can include).
