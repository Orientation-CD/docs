# 更新圆筑 AI 文档

将 docs 维护为适合初学者对照源码学习的双语教材。以当前实现为依据，重大变化优先重写；不能把更新降格为接口清单、变更摘要或源码链接汇总。

## 定位项目与读取入口

先解析本 skill 目录的真实路径（用户级入口可能是符号链接），再用 Git 确认所属 docs 仓库及远端。仓库身份和默认分支如下；用户本次明确指定的版本优先。

| 角色 | GitHub 仓库 | 默认分支 |
| --- | --- | --- |
| docs | `Orientation-CD/docs` | `main` |
| 前端 | `Orientation-CD/wechat_mini_program` | `ui-integration` |
| 后端 | `Orientation-CD/YuanZhu-AI` | `main` |

优先查找 docs 的同级应用仓库，并核对 Git 远端身份；工作区在其他位置时通过已配置项目或用户给定路径定位。目录名相同不代表仓库正确。不要写死本机路径，也不要因当前工作目录不同而更新其他项目。

开始时读取：

- [维护指南](../../../reference/maintenance.md)：来源工具、双语组织、站点验证与发布方式的权威操作入口。
- [来源版本记录](../../../sources/revisions.json)：上次核验版本、权威文件和日期。
- 各仓库适用的 `AGENTS.md`、docs 当前 scripts、共享导航、页面审计和 trace 记录。应用仓库的操作约定按实际操作范围适用，不把应用发布流程套到纯文档修改。

项目规则放在本 skill；命令细节继续维护在现有指南和工具中。读取它们的当前版本，不复制一套可能分叉的抽取器或发布脚本。

## 1. 固定审计版本

1. 检查三个仓库的工作区和 docs 分支。保留用户修改，在合适的 docs 工作分支上工作；需要隔离时使用独立 checkout/worktree。不要切换、重置或清理应用工作区来取得新代码。
2. 保存更新前的来源记录，获取指定远端分支的最新提交，解析完整 SHA。针对这对固定版本使用 `git show`、差异或独立源码导出审读，不能把落后的当前 checkout 或未提交改动当作该版本。
3. 先验证来源可访问及版本可解析。缺少仓库、权限或必要源码时，报告具体缺口；继续不依赖它的工作，但不能声称完成全量同步或凭候选契约补出实现。
4. 比较上次审计与新版本。先建立变更领域、受影响调用链和页面处理清单，再决定并行分工。独立领域可并行审读/写作，共享来源文件和最后的链接迁移由一个协调者统一处理。

## 2. 从源码确定事实

沿实际用户动作或外部请求阅读前端入口、请求封装、后端 handler、业务服务和后续执行；同时核对类型、模型、测试、迁移及契约。文档和 schema 可能滞后，遇到矛盾要继续读实际分支和调用方，明确证据及未解决之处。

必须区分：当前 UI 行为、公共 API 约束、供应商能力、仅前端候选契约、Mock、现存兼容适配器和已删除功能。一个前端 fixture 或 DTO 不能证明后端已实现；架构推荐入口不能替代当前 UI 实际调用的入口。

每个实际公开 API 都应能从接口索引进入两种语言的准确章节。公共机制可以复用章节，接口特有的调用方、权限、数据流、副作用、返回状态和失败恢复必须在本节讲清。

写作和源码审查时读取 [教学与全链路标准](references/teaching-standard.md)。先理解完整链路，再组织说明与图表。

## 3. 重建一致的双语教材

- 对架构、主旨或数据流已明显改变的页面，围绕最终实现整体重写。对局部变化精确修改；不要为保持旧段落而拼接相互矛盾的新旧模型。
- 对整个页面集合记录 `review`、`refresh`、`rewrite`、`add` 或 `migration` 等仓库支持的处理结果，未变化主题也要检查关联影响。同步英文与 `/zh/` 中文的主题、示例、图表、显式锚点和导航。
- 删除失效配置、旧教程和已移除模块的教学内容；历史地址按维护指南保留简短、`search: false` 的迁移入口。仍暴露或仍被 UI 使用的适配器准确归入兼容说明，不能为了“消除 legacy”隐去真实调用链。
- 同步概念页、教程、运维步骤、管理后台、接口和配置索引、数据模型、集成状态以及端到端链路。范围由源码影响决定，不只改 API 页或追着 diff 替换名词。
- 保留现有 VitePress 双语路径、`/docs/` 部署基路径、全局搜索、宽屏/移动端阅读与图表查看能力。导航分类随主题调整，避免没有入口的新增页面。

## 4. 更新可复现证据

遵循维护指南完成来源抽取、trace 记录和链接重定位；依赖关系如下：

1. 旧来源记录必须先保存。若重构使旧 trace 符号失效，先审查并更新真实 handler/符号映射；必要时适配抽取器，然后生成新快照。抽取失败需要解决，不能跳过检查或删掉仍存在接口的覆盖要求。
2. 仅在实际审读后更新核验日期、docs 基线和应用 SHA，并同步相应日期的页面审计记录。遵循现有 schema；不虚构审计结果。
3. 更新来源快照、两种语言的生成片段、接口/配置索引及每个公开 API 的 trace。生成文件通过现有工具更新，不手改输出掩盖源工具问题。
4. 所有写作者结束后，先对源码链接迁移执行只读报告，再写入可证明的映射。逐项核对未解析位置以及可见 `path:line` 标签；不能全局替换 SHA 后假定行号有效。

新内容的源码链接固定到已审计 SHA、实际文件和相关函数。来源快照能验证符号和链接存在，不能代替对执行顺序、事务边界与业务语义的源码审读。

## 5. 验证并交付

从维护指南和当前 package scripts 选择适用校验。一次完整同步应完成来源快照复现检查、来源抽取测试、`docs:check` 和浏览器测试；记录真实执行结果，不能将静态审读描述为已运行应用端到端测试。

浏览器验证覆盖双语搜索与导航、接口索引到章节、深链接、实际 Mermaid 语法、桌面宽屏/移动端及图表查看。文档预览使用自己的空闲端口，不抢占其他服务；不要同时运行会共用产物目录的浏览器套件。应用栈或真实供应商调用仅在任务需要且已有相应授权时进行。

交付前再检查指定上游分支是否推进。若有新提交，判断并审计与本次相关的差异，固定最终来源版本后重跑受影响检查；无法纳入时明确报告已覆盖 SHA 和剩余差异，不称为“全部最新”。不要无止境追逐移动分支。

交付包含：docs 分支与 PR、可用预览、重写/新增/迁移清单、来源版本、主要教学链路及验证结果和缺口。源码与内容确实无变化时报告核验结果，不制造空 PR 或仅为显得更新而修改日期。

默认将文档更新交付到 PR。用户明确要求合并/发布时再执行对应步骤，核对实际 PR 最新提交和检查结果，并沿用 main 的现有发布流程；过去某次发布的授权不自动扩展到下一次更新。
