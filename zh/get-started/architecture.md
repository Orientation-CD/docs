# 架构总览

本页给你整个系统是如何拼装在一起的**全局图景**。它刻意保持高层视角；每个组件在前端、后端、部署与参考章节中都有深入讲解。

## 各组件及其角色

### 1. 微信小程序（前端）

- 运行在用户手机的微信里。
- 用 **uni-app（Vue 3 + TypeScript + uview-plus）** 构建。
- 通过 **HTTPS** 与后端对话，使用会自动处理令牌刷新的 REST 客户端
  （`src/services/request.ts`）。
- 用后端签发的预签名 POST 表单，把照片**和**音频**直接上传到对象存储**（从不经过后端代理）。
- 在用户等待期间轮询后端查询设计任务状态。
- 两种编译期模式：**Mock**（自包含，用于 UI 开发）与
  **API**（生产行为）。参见
  [数据源模式](/frontend/data-source-modes)。

### 2. 后端（FastAPI）

一个 Python 3.12 FastAPI 应用，拥有全部业务逻辑：

- **REST API**——认证、设计任务、素材、计费、工作空间、报告、管理。每个路由都在 `/api/v1` 下。
- **ARQ worker**——后台任务处理器（见下）。
- **数据库访问**——PostgreSQL 之上的 SQLAlchemy 2.0 异步 ORM。
- **对象存储**——S3 兼容存储，存放照片、音频、效果图与报告素材。
- **微信集成**——登录 + 支付。

后端部署到**阿里云 SAE**，作为多个应用共享同一份不可变 Docker 镜像运行（参见[部署](/deploy/cloud-architecture)）。

### 3. ARQ worker

ARQ 是一个基于 Redis 的 Python 任务队列。后端运行两类 worker：

| Worker | 任务 | 做什么 |
| --- | --- | --- |
| **提交 worker** | `submit_provider_job` | 取一个已预留的设计任务，组装提供方请求（prompt + 图片/音频），调用 AI 提供方，并保存提供方的任务 id。 |
| **轮询 worker** | `poll_provider_job` | 反复询问 AI 提供方任务是否完成；完成后下载并持久化结果（图片或 markdown 文本），并把任务标记为完成。 |

worker 是**无状态**的，从 Redis 消费任务，因此可以独立扩缩。

### 4. AI 提供方

一个外部大模型——主图像提供方是 **Seedream**（封装在
`app/providers/` 中）；语音总结流程额外接入一个语音转写/摘要提供方。后端把提供方当作**异步 HTTP 服务**对待：提交 → 拿到
`provider_job_id` → 轮询 → 取结果。本地栈自带一个 **mock 提供方**，因此无需真实凭据就能跑通整条管线。

### 5. PostgreSQL

持久的系统记录库。它存储用户、会话、工作空间、设计任务、积分台账、计费订单/订阅、报告配置、素材元数据、分享/推荐邀请与法务文档同意记录。Schema 变更由
**Alembic** 迁移管理。

### 6. Redis

用于：

- **ARQ 任务队列**（提交与轮询任务）。
- **限流**（认证尝试、设计任务提交）。
- **进度指标**（展示给用户的滑动平均时长）。
- 短生命周期的协调/缓存状态。

### 7. 对象存储

存放所有二进制内容的 S3 兼容对象存储：

- 用户上传的**输入图片与音频**（在任务提交前有一个临时保留窗口）。
- **结果效果图**与 **markdown 总结文本**（作为任务输出存储）。
- **报告素材**与全局**法务文档**（隐私、条款）。

本地开发用 **MinIO**；生产用**阿里云 OSS**。前端只信任
`VITE_RESULT_STORAGE_ORIGINS` 中列出的结果媒体源站。

## 核心流程：一个设计任务

系统的心脏是**异步设计任务**。图像类功能与语音总结功能背后是同一个模式：

```
用户上传照片 / 录制音频
        │
        ▼
POST /api/v1/assets/upload-intents  （按素材，幂等）
        │
        ▼
直传到预签名 URL  ──►  POST /api/v1/assets/{id}/complete
        │
        ▼
POST /api/v1/design-jobs  （预留积分、创建任务、入队）
        │
        ▼
Redis 队列 ─► 提交 worker ─► AI 提供方（任务已创建）
        │
        ▼
轮询 worker ◄──► AI 提供方（任务完成了吗？）
        │
        ▼
结果图 / markdown 已持久化 ─► 任务状态 = completed
        │
        ▼
小程序轮询 GET /api/v1/design-jobs/{id} ─► 展示结果
```

完整的逐步追踪（写了哪些表、发生了哪些 HTTP 跳变），见
[设计任务生命周期](/reference/flows/design-job-lifecycle)。

## 资金流：积分与订阅

- 每个设计任务在提交时**预留**若干积分，任务结束时按实际成本**结算**。
- 用户通过微信支付购买**积分包**或**订阅**。
- 后端收到微信支付的**支付通知 webhook**，把订单标记为已支付，并发放积分 / 激活订阅。
- 当前版本中，订阅为**手动续订**；对已生效订阅提前续订在 UI 中被明确拒绝
  （"暂不支持提前续订"）。

## 认证模型

- 用户用**微信登录**认证（`wx.login` 的 code → 后端用它换取
  `openid`，首次注册时同时获取手机号）。
- 后端签发一个**access 令牌**（短期）与一个**refresh 令牌**（长期）。
- 小程序把令牌对存在本地存储的
  `yuanzhu.session.tokens.v1` 下，并在请求返回
  `401 AUTH_TOKEN_EXPIRED_OR_INVALID` 时自动刷新（单一共享的刷新 promise 合并并发 401）。

参见[认证](/backend/authentication)与
[微信登录流程](/reference/flows/wechat-login-flow)。
